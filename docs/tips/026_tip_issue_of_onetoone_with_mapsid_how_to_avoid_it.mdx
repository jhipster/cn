__Tip submitted by [@pmverma](https://github.com/pmverma)__

以下是关于使用 `@OneToOne` 与 `@MapsId` 的已知问题以及避免它的一些提示。

### 问题

假设你有一个 `Preference` 类，你已经用 `@OneToOne @MapsId` 将其关联到 `User`。

```java
class Preference {
    @OneToOne
    @MapsId
    private User user;
}
```

通常在 JHipster 中：

1. 当你为用户添加 `preference` 时，你将填写数据并从下拉列表中选择用户 `user01` 登录名并保存。
2. 如果你想编辑相同的 `preference`，你仍然可以选择用户，如果你这次选择 `user02`，那么在整个请求生命周期中，后端的 `preference` 对象中将有 `user02`。
3. 再次如果你重新加载相同的 `preference`，那么你会看到 `user01` 在那里，而不是 `user02`。

这里不正确的部分是：

**第 2 步中 `preference` 对象中的 `user02`。** `preference` 中的 user 对象应该始终引用 `user01`。

有关更多信息，请查看 [https://github.com/jhipster/generator-jhipster/issues/9100](https://github.com/jhipster/generator-jhipster/issues/9100)

### 避免它的提示

* 隐藏下拉列表并在**客户端**以编程方式在 `preference` 中设置当前用户。（同样，这种解决方案仅适用于 Preference、Settings、User Profile 等实体，在这些实体中选择用户的下拉列表没有意义。）
* 隐藏下拉列表并在**服务器端**以编程方式在 `preference` 中设置当前用户。（同样，这种解决方案仅适用于 Preference、Settings、User Profile 等实体，在这些实体中选择用户的下拉列表没有意义。JHipster 已经提供了获取当前用户的方法。）
* 在对该用户执行任何业务逻辑之前验证并加载正确的关联值。（同样，仅当你的逻辑依赖于 `preference.getUser()` 时才需要这样做）
* 如果你使用的是 Hibernate 5.4.2 及更高版本，那么你将获得正确的关联值，但仅在实体合并操作完成后。因此，如果你的业务逻辑在实体合并操作之前执行，你必须处理它，否则你可能会得到不正确的结果。
