__Tip submitted by [@tcharl](https://github.com/tcharl)__

_目标：_ JHipster 非常擅长管理你的模型实体，这要归功于其强大的领域特定语言。
但是，在自定义代码和生成世界之间找到最佳平衡始终是一项艰巨的任务。
以下是你可以采用的不同模式，以使其成为现实。


## 模式 1 - 生成一次

这种方法是最简单的，并且在大多数用例中使用。
它包括对实体建模一次，生成第一个模型，然后在第一次生成后覆盖你想要的内容。
如果有一天你想重新同步，你总是可以在另一个分支中重新生成，然后通过 IDE 比较两个代码。
但是，后面的过程总是很痛苦，你可能会花费数天时间进行重大升级。

### 优点

- 做你想做的

### 缺点

- 你会倾向于不从 JHipster 新功能中受益


## 模式 2 - 分离生成的代码和自定义代码

使用这种方法，你将尝试避免修改生成的类，并将自定义代码托管在专用类中。
在这里，你可以使用 --with-generated-flag jhipster CLI 选项，以便轻松区分生成的类和自定义类。
最后，你只需修改前端部分的主路由器，以便路由到自定义主页而不是生成的主页。

为了避免路由器文件在每次生成时被覆盖，你可以在项目根目录创建一个 `.yo-resolve` 文件，并告诉 yeoman 预期的行为。

示例：

```
src/main/resources/swagger/api.yml skip
src/main/webapp/app/modules/home/home.tsx skip
```

### 优点

- 可以在没有太多麻烦的情况下结合生成和自定义代码

### 缺点

- 死代码
- 自定义类的名称或包与你的模型不同（可以被视为 DDD 最佳实践，但仍然如此）。


## 模式 3 - 并行

在这里，目标是使用类扩展和 bean 优先级，以便注入自定义代码而不是生成的代码。

让我们以一个 `Customer` jhipster 实体为例。

### 仓库

在仓库级别，你将使用 `NoRepositoryBean` 注解标注 jhipster 生成的仓库以禁用发现。
然后你可以创建自定义仓库类

```
@Repository
@Primary
MemberRepositoryPrimary extends MemberRepository
```

### 服务

在这里，你将使用 `serviceImpl` 选项，以便能够在控制器中注入自定义 Bean。
然后，你可以简单地扩展生成的服务并用 `@Primary` 注解你的 bean 以获得优先级。

### 控制器

你将为自定义端点使用另一个 API 前缀（例如 `/api/v2`）。

### Angular

前端也适用相同的扩展，然后你可以在 `app.module.ts` 文件中配置你的 beans 优先级：
```
providers: [
// keep other entries
{ provide: MemberDomainService, useExisting: MemberDomainServicePrimary },
]
```

### 优点

- 可以覆盖生成的代码行为
- 易于查找自定义代码
- 即使对于自定义代码也保持 JHipster 最佳布局

### 缺点

- 文件重复

## 替代的并行方法

这种方法旨在向现有的 JHipster 应用程序添加功能，并对生成的代码进行最少的更改。

### 仓库层

在单独的自定义包中创建包含所有自定义方法的仓库接口。这种方法确保生成的仓库代码保持不变，同时你的自定义逻辑是有组织的和可维护的。

### 服务层

在此层添加自定义代码有三种主要方法：

面向切面编程（AOP）：

AOP 允许你引入横切关注点，如日志记录、安全性或事务管理，而无需更改核心业务逻辑。这种关注点分离有助于维护更清晰和更模块化的代码。

事件监听器：

如果新功能由应用程序中的特定事件触发（例如，在保存 Foo 实体之后），你可以使用 Spring 的事件监听器机制。这使核心逻辑保持干净，尽管它可能使执行流程更难追踪。

装饰器模式：

为了以受控方式添加新方法或修改现有行为，强烈推荐装饰器模式。这种模式涉及用提供附加功能的装饰器包装原始类。它干净、可测试，并且需要对原始客户端类进行最少的更改，确保更好的可维护性。

步骤 1：创建或扩展现有接口，具体取决于服务类的生成方式
```
interface IFooService {
    void newFeature();
    //Existing method declarations
   ...
}
```
步骤 2：通过组合进行扩展
```
@Service
@Qualifier("entended") 
public class ExtendedFooService implements FooService{
    private final FooService existingFooService;
    private final ExtendedFooRepository extendedFooRepository; // For new repository functionality
   ...
}
```
步骤 3：将 @Primary 添加到现有服务类，并将现有服务类标记为步骤 1 中接口的实现。

步骤 4：将原始服务客户端的属性类型更改为步骤 1 中创建的接口。

如果你不太可能有服务方法的多个实现或不期望服务方法频繁更改，你可以省略步骤 1 并在后续步骤中调整相关更改以简化此方法的实现。

### Web 层

创建新的端点控制器。
```
@RestController
@RequestMapping("/api/extended/foo")
public class ExtendedFooController {
    private final ExtendedFooService extendedFooService;
    
    public ExtendedFooController(ExtendedFooService extendedFooService) {
        this.extendedFooService = extendedFooService;
    }

    // New endpoints
    @GetMapping("/new-feature")
    public ResponseEntity<?> newFeature() {
        // Implementation
    }
}
```
