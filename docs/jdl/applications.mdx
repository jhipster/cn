## 语法

应用程序声明如下所示：

```jdl
application {
  config {
    <application option name> <application option value>
  }
  [entities <application entity list>]
  [<options>]
}
```

- 应用程序配置的键/值在 `config` 下指定（必须在 `application` 内）
- 可以有 0、1 或任意数量的应用程序选项（只要它们是有效的）
- 将在应用程序内生成的实体通过 `entities` 列出，这是在应用程序中生成实体的推荐方式。
  - 这可以省略，但在应用程序内生成实体需要：
    - 从应用程序内的另一个 JDL 文件
    - 或使用 CLI
- `entities` 关键字是可选的：您可以省略它，但 JDL 文件中的每个实体都将在应用程序内生成
- 应用程序可以有常规选项（如 `dto` 或 `service`），更多信息请参阅[下一节](#应用程序中的选项)。


## 应用程序中的选项

JDL 应用程序支持选项声明（`dto`、`service`、`skipServer` 等），但有一些规则。

假设我们有这个 JDL 文件：

```jdl
application {
  config {
    baseName app1
  }
  entities A, B, C
  dto * with mapstruct
}

application {
  config {
    baseName app2
  }
  entities C, D
  paginate * with pagination except D 
}

application {
  config {
    baseName app3
  }
  entities * except A, B, C, D, F
  service * with serviceClass
}

entity A
entity B
entity C
entity D
entity E
entity F

paginate * with infinite-scroll
```

在此示例中，我们可以看到一些内容：

- JDL 文件中声明了 6 个实体：`A、B、C、D、E 和 F`。
- 我们有 3 个应用程序：`app1、app2 和 app3`
  - `app1` 使用 `A、B 和 C`
  - `app2` 使用 `C 和 D`
  - `app3` 使用 `E`（`* except A, B, C, D, F`）
- 这些应用程序中的每一个都声明了选项，还声明了一个**全局**选项。
  - `app1` 为 `A、B 和 C` 使用 `dto`
  - `app2` 为 `C` 使用 `paginate`（因为有异常）
  - `app3` 为 `E` 使用 `service`
  - 全局选项也使用 `pagination`（对于每个实体）

以下是文件生成的方式：

- `app1`
  - `A`: 将使用 `paginate with infinite-scroll`（全局选项不会被本地选项覆盖）和 `dto with mapstruct`
  - `B`: 将使用相同的选项
  - `C`: 也将使用相同的选项
- `app2`:
  - `C`: 将使用 `paginate with pagination`（而不是 `infinite-scroll`，因为本地选项优先）
  - `D`: 将使用 `paginate with infinite-scroll`，因为前面的选项不包括 `D`
- `app3`:
  - `E`: 将使用 `paginate with infinite-scroll` 和 `service E with serviceClass`

此示例说明了**遮蔽**原则。支持全局选项，每个声明的应用程序都将使用全局选项，**除非**在应用程序中也声明了选项。

另请注意从 `app3` 中的前一个示例中提取的代码片段：

```jdl
entities * except A, B, C, D, F
service * with serviceClass
```

这基本上意味着 `app3` 将只使用 `E`，应用程序的实体将使用 `service` 选项，这意味着 `E` 而不是 `A 到 F`。

最后，有一个 `F` 实体不在任何应用程序中，因此不会生成此实体。

_注意：目前支持所有常规选项。_


## 示例

### 基本示例

```jdl
application {
  config {
    baseName exampleApp
    applicationType gateway
  }
}
```

### 多个应用程序

```jdl
application {
  config {
    baseName exampleApp1
    applicationType microservice
    serverPort 9001
  }
}

application {
  config {
    baseName exampleApp2
    applicationType microservice
    serverPort 9002
  }
}

application {
  config {
    baseName exampleApp3
    applicationType gateway
    serverPort 9000
  }
}
```

### 包含实体

```jdl
application {
  config {
    baseName exampleApp1
    applicationType microservice
    serverPort 9001
  }
  entities A
}

application {
  config {
    baseName exampleApp2
    applicationType microservice
    serverPort 9002
  }
  entities * except A
}

entity A
entity B
entity C
```

### 包含选项

```jdl
application {
  config {
    baseName exampleApp1
    applicationType microservice
    serverPort 9001
  }
  entities A
  dto A with mapstruct 
}

application {
  config {
    baseName exampleApp2
    applicationType microservice
    serverPort 9002
  }
  entities * except A
  paginate C with pagination
}

entity A
entity B
entity C
```


## 完整示例分解

示例 1：

```jdl
application {
  config {
    baseName myMonolith
    applicationType monolith
  }
  entities * except C, D
}
application {
  config {
    baseName myGateway
    applicationType gateway
    serverPort 9042
  }
  entities * except A, B
}
application {
  config {
    baseName microserviceA
    applicationType microservice
  }
  entities C
}
application {
  config {
    baseName microserviceB
    applicationType microservice
    serverPort 8082
  }
  entities D
}
entity A
entity B
entity C
entity D
dto * with mapstruct
service * with serviceClass
paginate D with pagination
```

现在，在生成这些应用程序和文件夹时将会发生以下情况：

- 将创建四个应用程序：
  - myMonolith 在 `./myMonolith` 中，服务器端口为 `8080`
  - myGateway 在 `./myGateway` 中，服务器端口为 `9042`
  - microserviceA 在 `./microserviceA` 中，服务器端口为 `8081`
    - 尽管我们没有指定服务器端口，但 JHipster 默认设置了一个。
    - 对于微服务，默认端口是 `8081`
    - 对于网关和单体应用，默认端口是 `8080`
  - microserviceB 在 `./microserviceB` 中，服务器端口为 `8082`
- 将生成四个实体
  - `A` 和 `B` 在单体应用中
  - `C` 和 `D` 都在网关中
    - `C` 在第一个微服务中
    - `D` 在第二个微服务中
- `microservice` 选项对于 `C` 和 `D` 是隐式的
  - 因为它们在两个微服务上生成，所以这个选项将默认设置。
- 选项的工作方式与以前相同

请注意，生成器会设置默认值（如 `databaseType`），如果它们不存在的话。
JHipster Core 为您做的完全相同的事情。

## 微服务工作流

处理微服务几乎是复杂的，但 JDL 为您提供了一些选项来按您的意愿处理您的实体。
使用 `microservice <ENTITIES> with <MICROSERVICE_APP_NAME>`，您可以指定哪个实体在哪个微服务中生成。

以此设置为例：

```
entity A
entity B
entity C
microservice A with firstMS
microservice B with secondMS
```

给定两个 JHipster 应用程序（'firstMS' 和 'secondMS'），如果您在这两个应用程序中导入 JDL 文件，您将得到以下结果：

- 在 'firstMS' 中，将生成实体 `A` 和 `C`。
- 在 'secondMS' 中，将生成实体 `B` 和 `C`。

`C` 在两个应用中都会生成，因为如果没有微服务选项指定此实体在哪里生成，它将在所有地方生成。

如果您决定在单体应用中导入此 JDL，将生成每个实体（单体应用在 JDL 中没有限制选项）。

_注意：如果您希望在两个不同的微服务中生成相同的实体，您可以编写两个 JDL 文件，而不是更新 JDL 文件。每次都是如此。_

前面的示例不能这样写：

```
entity A
entity B
entity C
microservice * except B with firstMS
microservice * except A with secondMS
```

结果如下：

- 在 'firstMS' 中，只会生成实体 `C`
- 在 'secondMS' 中，将生成实体 `B` 和 `C`。

这是因为，在解析时，如果一个选项与另一个选项重叠，后者优先。
您也可以使用 JDL 创建整个微服务堆栈，[请参阅此博客文章](https://medium.com/@deepu105/create-full-microservice-stack-using-jhipster-domain-language-under-30-minutes-ecc6e7fc3f77)以获取示例
