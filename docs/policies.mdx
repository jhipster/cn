JHipster 开发团队遵循一些编码策略。您可以将它们视为"最佳实践"或"指南"。它们仅在项目本身上执行，而不是在生成的代码上：如果您使用 JHipster 生成项目，则绝对不必遵循它们！

这些策略由[开发团队](/team)遵循，如果您提交 Pull Request，则应遵循它们。


## 策略 0：策略由开发团队投票决定

每个策略都可以由开发团队在[邮件列表](https://groups.google.com/forum/?hl=en#!forum/jhipster-dev)上讨论或修改。任何重大更改都必须投票（同意则 +1，不同意则 -1）。


## 策略 1：JHipster 使用的技术尽可能使用其默认配置和最佳实践

例如，我们以"通常的方式"使用 JPA、Spring、Angular 和 React，没有一些繁重的配置选项，并使用它们通常的命名和编码约定。我们这样做是因为：

- 每种技术通常都有很好的理由使用这些默认值
- 如果我们不重新配置所有内容，就更容易理解 JHipster 的工作原理

我们可能仅在默认配置与 JHipster 使用的其他技术产生问题时才更改它。例如，为了让 Spring Security 和 Angular 一起工作，我们不得不更改 Spring Security 的默认配置，或者如果默认配置使我们的 EJS 模板变得极其复杂


## 策略 2：仅在生成的代码中有足够附加值时才添加选项/功能

JHipster 在生成项目时有许多选项。我们仅在这些选项复杂并涉及配置或编码多个组件时才添加它们。

仅因为节省几行代码而添加选项并不是 JHipster 的良好用法：

- 手动编写这些代码比学习新的 JHipster 选项更容易
- 它只会使我们的生成器更复杂，而不会增加任何价值


## 策略 3：对服务器端和客户端的第三方库使用严格版本

唯一的例外是对我们库的依赖，其中相对版本效果更好。我们在库版本上遇到了许多冲突问题。这主要是一个 JavaScript 问题，所以要明确：我们在生成的 `package.json` 文件中使用固定的库版本。


## 策略 4：我们尽可能在为同一目的提供的不同选项之间提供相似的用户/开发者体验

JHipster 的一个重要方面是我们的用户和开发者体验，以及您可以轻松地将一种技术交换为另一种技术（例如：客户端框架、身份验证、数据库等），因此，如果它们的配置/编码尽可能相似，对开发者来说会更容易。当违反其他策略时，我们可以例外。


## 策略 5：开发者体验可以优先于策略 1、2、3 和 4

这意味着我们需要确保开发者体验尽可能不受以下影响：

- 功能添加
- 炒作驱动的开发
- 贡献者便利性
- 技术热情

开发者体验是主观的，因此以下内容可以作为 JHipster 社区的粗略指南。这将是使用 JHipster 作为产品和平台的整体体验。包括：

- JHipster CLI 体验（易用性、直观性、速度等）
- 生成的代码（质量、简洁性、可读性、易维护性、可升级性、熟悉度等）
- 工具的用户体验，如 JHipster online、JDL studio
- 文档（网站和生成的 Readme）

当在执行此策略上存在分歧时，可以在[邮件列表](https://groups.google.com/forum/?hl=en#!forum/jhipster-dev)上进行逐案辩论和投票来解决。
