# JHipster API 网关

JHipster 可以生成 API 网关。网关是一个正常的 JHipster 应用程序，您可以在该项目上使用常规的 JHipster 选项和开发工作流，但它也作为您微服务的入口。更具体地说，它为所有微服务提供 HTTP 路由和负载均衡、服务质量、安全性和 API 文档。

## 使用网关进行 HTTP 请求路由

当网关和微服务启动时，它们将在 Consul 服务注册中心中注册自己。

网关将使用微服务的应用程序名称自动代理所有请求到微服务：例如，当微服务 `app1` 被注册时，它在网关上的 `/services/app1` URL 上可用。

例如，如果您的网关在 `localhost:8080` 上运行，您可以指向 [http://localhost:8080/services/app1/api/foos](http://localhost:8080/services/app1/api/foos) 来
获取由微服务 `app1` 提供的 `foos` 资源。如果您尝试使用 Web 浏览器执行此操作，请不要忘记 REST 资源在 JHipster 中默认受安全保护，因此您需要发送正确的 JWT 头（请参见下面的安全部分），或在微服务的 `SecurityConfiguration` 类中删除这些 URL 的安全性。

如果同一服务的多个实例正在运行，网关将从服务注册中心获取这些实例，并使用 [Consul](https://www.consul.io/use-cases/load-balancing) 进行 HTTP 请求的负载均衡。您可以在 [http://localhost:8080/api/gateway/routes](http://localhost:8080/api/gateway/routes) 查看运行中的微服务的详细列表，包括它们的 IP 地址、Git 版本、状态等。此端点受安全保护。

每个网关都有一个特定的“管理 > 网关”菜单，可以在其中监控打开的 HTTP 路由和微服务实例。


## 安全

标准的 JHipster 安全选项在[此安全文档页面](/security/)上有详细说明。然而，保护微服务架构有一些特定的调整和选项，这里详细说明。

### JWT（JSON Web Token）

JWT（JSON Web Token）是一个行业标准，是在微服务架构中保护应用程序的易于使用的方法。

JHipster 使用由 Okta 提供的 [JJWT 库](https://github.com/jwtk/jjwt)来实现 JWT。

令牌由网关生成，并发送到底层微服务：由于它们共享一个共同的秘密密钥，微服务能够验证令牌，并使用该令牌对用户进行身份验证。

这些令牌是自足的：它们具有身份验证和授权信息，因此微服务不需要查询数据库或外部系统。这对于确保可扩展的架构很重要。

为了使安全性正常工作，必须在所有应用程序之间共享 JWT 秘密令牌。

- 对于每个应用程序，默认令牌是唯一的，由 JHipster 生成。它存储在 `.yo-rc.json` 文件中。
- 令牌在 `src/main/resources/config/application.yml` 文件中使用 `jhipster.security.authentication.jwt.secret` 键进行配置。
- 要在所有应用程序之间共享此密钥，请将密钥从您的网关复制到所有微服务，或使用 [JHipster 的 Consul K/V 存储特定配置](/consul/) 共享它。这是人们使用这些中央配置服务器的主要原因之一。
- 一个好的做法是在开发和生产中使用不同的密钥。

### OpenID Connect

JHipster 提供 OpenID Connect 支持，如我们的 [OpenID Connect 文档](/security/#oauth-20-and-openid-connect)中所详述。

当选择此选项时，您将默认使用 Keycloak，您可能希望使用 Docker Compose 运行您的完整微服务架构：请务必阅读我们的 [Docker Compose 文档](/docker-compose/)，并为 Keycloak 正确配置您的 `/etc/hosts`。

使用 OpenID Connect 时，JHipster 网关将向微服务发送 OAuth2 令牌，微服务将接受这些令牌，因为它们也连接到 Keycloak。

与 JWT 不同，这些令牌不是自足的，应该是有状态的，这会导致以下问题：

- 微服务中的性能问题：由于查找当前用户的安全信息非常常见（否则我们一开始就不会使用任何安全选项），每个微服务都将调用 OpenID Connect 服务器来获取该数据。因此，在正常设置中，这些调用将由每个微服务在每次获得请求时进行，这将很快导致性能问题。
  - 如果您在生成 JHipster 微服务时选择了缓存选项（[这里是“使用缓存”文档](/using-cache/)），将生成一个特定的 `CachedUserInfoTokenServices` Spring Bean，它将缓存这些调用。当正确调整时，这将消除性能问题。
  - 如果您需要有关此“用户信息”请求的更多信息，它在您的 `src/main/resources/application.yml` 配置文件中使用标准 Spring Boot 配置键 `security.oauth2.resource.userInfoUri` 进行配置。


## 自动文档化

网关公开它代理的服务的 Swagger API 定义，因此您可以从像 Swagger UI 和 swagger-codegen 这样的有用工具中受益。

网关的“管理 > API”菜单有一个特定的下拉列表，显示网关的 API 和所有来自注册微服务的 API。

使用这个下拉列表，所有微服务 API 都会自动文档化，并可以从网关进行测试。

当使用安全 API 时，安全令牌会自动添加到 Swagger UI 界面，因此所有请求都可以开箱即用。


## 速率限制

这是一个高级功能，使用 [Bucket4j](https://github.com/vladimir-bukhtoyarov/bucket4j) 和 [Hazelcast](https://hazelcast.com/) 在微服务上提供服务质量。

网关提供速率限制功能，因此 REST 请求的数量可以被限制：

- 按 IP 地址（对于匿名用户）
- 按用户登录（对于已登录用户）

JHipster 将使用 [Bucket4j](https://github.com/vladimir-bukhtoyarov/bucket4j) 和 [Hazelcast](https://hazelcast.com/) 来计算请求数量，并在超过限制时发送 HTTP 429（请求太多）错误。每个用户的默认限制是每小时 100,000 次 API 调用。

这是一个重要功能，可以保护微服务架构不被特定用户的请求洪水攻击。

由于网关保护 REST 端点，它可以完全访问用户的安全信息，因此可以扩展以根据用户的安全角色提供特定的速率限制。

要启用速率限制，请打开 `application-dev.yml` 或 `application-prod.yml` 文件并将 `enabled` 设置为 `true`：

```yaml
jhipster:
    gateway:
        rate-limiting:
            enabled: true
```

数据存储在 Hazelcast 中，因此只要配置了 Hazelcast 分布式缓存，就可以扩展网关，这应该开箱即用：

- 所有网关默认都配置了 Hazelcast

如果您想添加更多规则或修改现有规则，您需要在 `RateLimitingFilter` 类中编写它们。修改的示例可能包括：

- 降低 HTTP 调用的限制
- 添加每分钟或每天的限制
- 对“admin”用户删除所有限制


## 访问控制策略

默认情况下，所有注册的微服务都可以通过网关访问。如果您想排除特定 API 通过网关公开，您可以使用网关的特定访问控制策略过滤器。可以在 `application-*.yml` 文件中使用 `jhipster.gateway.authorized-microservices-endpoints` 键进行配置：

```yaml
jhipster:
    gateway:
        authorized-microservices-endpoints: # Access Control Policy, if left empty for a route, all endpoints will be accessible
            app1: /api,/v2/api-docs # recommended dev configuration
```

例如，如果您只希望微服务 `bar` 的 `/api/foo` 端点可用：

```yaml
jhipster:
    gateway:
        authorized-microservices-endpoints:
            bar: /api/foo
```


## 为网关安全启用 TLS

默认情况下，网关通过不安全的 HTTP 运行。对于生产环境，建议启用 TLS 以增强安全性。要这样做，请在 `application-prod.yml` 下取消注释提供的代码片段。这将使用位于 `config/tls` 中文件名为 `keystore.p12` 的自签名 TLS 证书，或者您可以使用预定义密码指定您自己的密钥库。

```yaml
server:
    port: 443
    ssl:
      key-store: classpath:config/tls/keystore.p12
        key-store-password: password
        key-store-type: PKCS12
          key-alias: selfsigned
        # The ciphers suite enforce the security by deactivating some old and deprecated SSL cipher, this list was tested against SSL Labs (https://www.ssllabs.com/ssltest/)
        ciphers: TLS_ECDHE_RSA_WITH_AES_128_CBC_SHA,TLS_ECDHE_RSA_WITH_AES_256_CBC_SHA,TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256,TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384 ,TLS_DHE_RSA_WITH_AES_128_GCM_SHA256 ,TLS_DHE_RSA_WITH_AES_256_GCM_SHA384 ,TLS_ECDHE_RSA_WITH_AES_128_CBC_SHA256,TLS_ECDHE_RSA_WITH_AES_256_CBC_SHA384,TLS_DHE_RSA_WITH_AES_128_CBC_SHA256,TLS_DHE_RSA_WITH_AES_128_CBC_SHA,TLS_DHE_RSA_WITH_AES_256_CBC_SHA256,TLS_DHE_RSA_WITH_AES_256_CBC_SHA,TLS_RSA_WITH_AES_128_GCM_SHA256,TLS_RSA_WITH_AES_256_GCM_SHA384,TLS_RSA_WITH_AES_128_CBC_SHA256,TLS_RSA_WITH_AES_256_CBC_SHA256,TLS_RSA_WITH_AES_128_CBC_SHA,TLS_RSA_WITH_AES_256_CBC_SHA,TLS_DHE_RSA_WITH_CAMELLIA_256_CBC_SHA,TLS_RSA_WITH_CAMELLIA_256_CBC_SHA,TLS_DHE_RSA_WITH_CAMELLIA_128_CBC_SHA,TLS_RSA_WITH_CAMELLIA_128_CBC_SHA
```

请记住，在服务器上启用 TLS 可能会带来一些性能开销。如果可能，请考虑在网关外使用具有 SSL 终止的负载均衡器来处理加密，这可以帮助减轻这种性能影响。
