## 概述

JHipster 应用程序和相关服务可以通过以下方式部署：

- 标准 kubectl/kustomize/skaffold 子生成器 `jhipster kubernetes|k8s`
- Helm 子生成器 `jhipster kubernetes-helm|helm-k8s`
- Knative 子生成器 `jhipster kubernetes-knative|knative`

```shell
jhipster kubernetes | k8s
```

此子生成器生成通过 `kubectl/kustomize/skaffold cli` 部署到 [Kubernetes](http://kubernetes.io/) 的清单文件。

[![kubernetes](/images/logo/logo-kubernetes.png)](http://kubernetes.io/)


## 限制

- 尚不支持 Cassandra
- 需要 Kubernetes v1.9+


## 先决条件

您必须安装：

- [Docker](https://docs.docker.com/installation/#installation)
- [kubectl](http://kubernetes.io/docs/user-guide/prereqs/)

您必须有一个 Docker 注册表。如果您没有，可以使用官方的 [Docker Hub](https://hub.docker.com/)。


## Minikube

[Minikube](https://github.com/kubernetes/minikube) 是一个帮助在本地运行 Kubernetes 的工具。Minikube 在您的笔记本电脑上的 VM 内运行单节点 Kubernetes 集群，供希望尝试 Kubernetes 或日常开发的用户使用。

您可以使用它在推送到 [Kubernetes](http://kubernetes.io/) 之前测试您的应用程序。


## 运行子生成器

要为 Kubernetes 生成配置文件，请在新文件夹中运行此命令：

```shell
jhipster kubernetes | k8s
```

然后回答所有问题来部署您的应用程序。

### 您希望部署哪种*类型*的应用程序？

您的应用程序类型取决于您是希望部署微服务架构还是经典应用程序。

### 输入您的应用程序所在的根目录

输入路径。

### 您希望在 Kubernetes 配置中包含哪些应用程序？

选择您的应用程序。

### 您希望为您的应用程序设置监控吗？

选择选项。

### 输入用于保护 JHipster Registry 管理员的管理员密码

此问题仅在您选择带有 JHipster Registry 的微服务架构时显示。

### 我们应该使用什么作为 Kubernetes 命名空间？

查看[命名空间文档](http://kubernetes.io/docs/user-guide/namespaces/)

### 我们应该使用什么作为基本 Docker 仓库名称？

如果您选择 [Docker Hub](https://hub.docker.com/) 作为主注册表，它将是您的 Docker Hub 登录名。

如果您选择 [Google Container Registry](https://cloud.google.com/container-registry/)，那么它将是 `gcr.io/[PROJECT ID]`，或区域注册表，如 `eu.gcr.io/[PROJECT ID]`、`us.gcr.io/[PROJECT ID]` 或 `asia.gcr.io/[PROJECT ID]`。有关更多详细信息，请参阅[推送和拉取镜像](https://cloud.google.com/container-registry/docs/pushing-and-pulling)。

如果您选择其他注册表，如 [Harbor](https://goharbor.io/)、[Quay](https://www.openshift.com/products/quay) 或类似的东西，那么登录名将像 `<registry_server>/<repo>/[PROJECT ID]`

### 我们应该使用什么命令将 Docker 镜像推送到仓库？

推送到 Docker Hub 的默认命令是 `docker image push`

如果您使用 Google Container Registry 发布您的 Docker 镜像，它将是：`gcloud docker push`

### 为您的边缘服务选择 Kubernetes 服务类型？

选择适当的 K8s 路由类型。

这些是标准提示。此外，根据选择 Istio、Ingress 等选项，将显示其他提示。


## 更新您已部署的应用程序

### 准备新部署

当您的应用程序已经部署后，您可以通过构建新的 Docker 镜像来重新部署它：

```shell
./mvnw package -Pprod -DskipTests jib:dockerBuild
```

或使用 Gradle 时：

```shell
./gradlew -Pprod bootJar jibDockerBuild -x test
```

### 推送到 Docker Hub

在本地标记您的镜像：

```shell
docker image tag application username/application
```

将您的镜像推送到 Docker Hub：

```shell
docker image push username/application
```


## 部署单体/微服务应用程序

您可以通过运行以下命令来部署所有应用程序：

```shell
./kubectl-apply.sh -f (default option)  [or] ./kubectl-apply.sh -k (kustomize option) [or] ./kubectl-apply.sh -s (skaffold run)
```

您可以使用 kustomize 部署应用程序：

```shell
kubectl apply -k ./
```

您可以使用 skaffold 部署应用程序：

```shell
skaffold run [or] skaffold deploy
```

它将部署您的应用程序及其相关的依赖服务（数据库、elasticsearch 等）。

### 自定义命名空间

可以为整个部署指定自定义命名空间。要执行自定义命令，您必须指定目标命名空间，如此示例：

```shell
kubectl get pods -n <custom-namespace>
```

### 扩展您的部署

您可以使用以下命令扩展您的应用程序：

```shell
kubectl scale deployment <app-name> --replicas <replica-count>
```

### 零停机部署

在 Kubernetes 中更新正在运行的应用程序的默认方法是将新的镜像标签部署到您的 Docker 注册表，然后使用以下命令部署它：

```shell
kubectl set image deployment/<app-name>-app <app-name>=<new-image>
```

使用 livenessProbes 和 readinessProbe 允许您告诉 Kubernetes 您的应用程序的状态，以确保您的服务的可用性。如果您希望实现零停机部署，您需要为每个应用程序至少拥有 2 个副本。这是因为滚动升级策略首先停止正在运行的副本以放置新的副本。仅运行一个副本将在升级期间导致短暂停机。

### 在 Kubernetes 中部署服务注册中心

尽管 Kubernetes 通过 **Kube-DNS** 拥有自己的内部服务发现功能，但 JHipster 依赖 Spring Cloud 进行服务发现，因此它依赖于第三方服务注册中心，如 Eureka 或 Consul。这样做的优势是平台无关，并且在生产环境和本地开发机器上的工作方式相似。

因此，对于微服务应用程序，JHipster Kubernetes 子生成器将生成 Kubernetes 清单文件来部署服务注册中心，如 **JHipster-Registry**（基于 Eureka）或 **Consul**。此外，生成的微服务和网关 Kubernetes 清单将包含适当的配置，以便将自己注册到其中央注册中心。

### 在 Kubernetes 中管理 JHipster Registry 或 Consul

对于 JHipster Registry 和 Consul，提供了 [StatefulSets](https://kubernetes.io/docs/concepts/abstractions/controllers/statefulsets/) 配置。这些是一种特定类型的 Kubernetes 资源，可以处理有状态应用程序，并允许您扩展服务注册中心以实现高可用性。有关 Eureka 和 Consul 高可用性的更多信息，请参阅它们各自的文档。

### 在 Kubernetes 中的集中化配置

集中化配置也是使用 **Spring Cloud Config Server**（使用 JHipster Registry 时）或 **Consul Key/Value 存储**（使用 Consul 时）进行设置。默认情况下，两个配置服务器都从 Kubernetes [ConfigMap](http://kubernetes.io/docs/user-guide/configmap/) 加载其配置，该配置包含以下格式的属性文件：

```
apiVersion: v1
kind: ConfigMap
metadata:
  name: application-config
  namespace: default
data:
  application.yml: |- # global properties shared by all applications
    jhipster:
      security:
        authentication:
          jwt:
            secret: secret
  gateway-prod.yml: |- # gateway application properties for the "prod" profile
    foo:
      bar: foobar
```

默认情况下，配置服务器在开发模式下运行，这意味着 YAML 属性文件直接从文件系统读取，并在更改时热重载。对于生产环境，建议从 Git 仓库设置配置，如我们的微服务文档中介绍的 [JHipster-Registry 配置服务器](/jhipster-registry) 和 [Consul 配置服务器](/consul)。

### 公开无头服务

注册中心在 Kubernetes 中使用无头服务部署，因此主服务没有 IP 地址，也无法获得节点端口。您可以使用以下方式为任何类型创建辅助服务：

```shell
kubectl expose service jhipster-registry --type=NodePort --name=exposed-registry
```

并使用以下方式探索详细信息：

```shell
kubectl get svc exposed-registry
```

要扩展 JHipster Registry，使用：

```shell
kubectl scale statefulset jhipster-registry --replicas 3
```

## 利用 Kubernetes 的优势

Kubernetes 开箱即用地提供了许多功能来帮助微服务部署，例如：
* 服务注册 - Kubernetes `Service` 是一等公民，通过 DNS 名称提供服务注册和查找。
* 负载均衡 - Kubernetes Service 充当 L4 负载均衡器。
* 健康检查 - Liveness 探针和 readiness 探针帮助确定服务的健康状态。
* 配置 - Kubernetes `ConfigMap` 可用于在应用程序外部存储和应用配置。

使用 Kubernetes 功能的许多优点：
* 简化部署
* 无需额外的 Eureka/Consul 部署
* 无需 Spring Cloud Gateway 来代理/路由请求
* 无需 Spring Cloud Load Balancer

同时，也有一些缺点：
* 无法通过 JHipster Registry 进行应用程序管理 - 此功能依赖于 Spring Cloud 的 `DiscoveryClient`。将来可以更新以添加 `spring-cloud-kubernetes`
* 无本地 Docker Compose 支持 - 您必须使用 `minikube` 进行本地开发，并使用 Ingress 路由流量
* 无请求级负载均衡 - Kubernetes Service 是 L4 负载均衡器，每个连接进行负载均衡。使用 Istio 进行请求级负载均衡（见下文）。

### 使用 Kubernetes 作为服务注册中心

要避免依赖 Eureka 或 Consul，您需要完全禁用服务发现
* 当被问及 `Which service discovery server do you want to use?` 时，选择 `No service discovery`

JHipster Gateway 通常在 API 调用前面，并使用 Spring Cloud Gateway 路由这些调用。没有服务注册中心，通过 Spring Cloud Gateway 进行路由将无法工作。您需要使用 Kubernetes Ingress 将流量路由到微服务。
* 当被问及 `Choose the kubernetes service type for your edge services` 时，选择 `Ingress`。


## Istio

您可以将微服务部署到启用了 [Istio](https://istio.io) 的 Kubernetes 集群中。当 Kubernetes 管理微服务部署和配置时，Istio 可以管理服务与服务之间的通信，如请求级负载均衡、重试、断路器、流量路由/分割等。

要启用 Istio 支持：
* 当被问及 `Do you want to configure Istio?` 时，选择其中一个 Istio 选项
* 当被问及 `Do you want to generate Istio route files` 时，选择 `Yes` 来生成断路等的默认配置


## 故障排除

> 我的应用程序无法被拉取，因为 'imagePullBackoff'

检查您的 Kubernetes 集群正在访问的注册表。如果您使用私有注册表，您应该通过 `kubectl create secret docker-registry` 将其添加到您的命名空间（有关更多信息，请查看[文档](https://kubernetes.io/docs/tasks/configure-pod-container/pull-image-private-registry/)）。

> 我的应用程序在能够启动之前就被停止了

这可能发生在您的集群资源低（例如 Minikube）时。增加您部署的 livenessProbe 的 `initialDelySeconds` 值。

> 尽管我有一个拥有许多资源的集群，但我的应用程序启动非常缓慢

默认设置针对中等规模的集群进行了优化。您可以自由增加 JAVA_OPTS 环境变量、资源请求和限制来提高性能。要小心！

> 我选择了 Prometheus，但没有目标可见

这取决于 Prometheus 操作器的设置和集群中的访问控制策略。RBAC 设置需要 1.6.0+ 版本才能工作。

> 我选择了 Prometheus，但我的目标从未被抽取

这意味着您的应用程序可能不是使用 Maven/Gradle 中的 `prometheus` 配置文件构建的

> 我的基于 SQL 的微服务在运行多个副本时在 Liquibase 初始化期间卡住了

有时数据库更改日志锁会损坏。您需要使用 `kubectl exec -it` 连接到数据库，并删除 liquibases `databasechangeloglock` 表的所有行。


## JHipster Kubernetes-helm

```shell
jhipster kubernetes-helm | k8s-helm
```

此子生成器生成通过 `helm cli` 部署到 [Kubernetes](http://kubernetes.io/) 的清单文件。


## Kubernetes-helm 先决条件

要使用此子生成器生成的清单，应该安装 `helm cli`。请遵循[此链接](https://github.com/helm/helm)获取安装说明。这需要 `helm 2.12.x 或更高版本`。

安装 Helm 后，您需要添加以下仓库：

```shell
helm repo add stable https://kubernetes-charts.storage.googleapis.com
helm repo add incubator https://kubernetes-charts-incubator.storage.googleapis.com
```

这些仓库应该添加到本地缓存，因为此子生成器将从上述仓库中拉取稳定的生产级服务图表。

此子生成器使用 `kubernetes` 子生成器来生成应用程序清单，并从上述仓库中拉取您的应用程序中引用的数据库、elasticsearch、prometheus 等服务镜像。


## Kubernetes-helm 部署

您可以通过运行以下命令来部署所有应用程序：

```shell
bash helm-apply.sh (or) ./helm-apply.sh
```

`helm-apply.sh` 将始终执行干净安装。任何具有相同标识的现有图表都会首先被删除，然后执行干净安装。

您可以通过运行以下命令来升级所有应用程序（如果您对生成的清单做了任何更改）：

```shell
bash helm-upgrade.sh (or) ./helm-upgrade.sh
```


## JHipster Kubernetes-knative

```shell
jhipster kubernetes-knative | knative
```

此子生成器生成通过 `kubectl 或 helm cli` 部署到 [Kubernetes](http://kubernetes.io/) 的清单文件。它根据选择的提示响应为其中一个 cli 生成清单。


## Kubernetes-knative 先决条件

此子生成器依赖于 Istio。为了使用此子生成器生成的清单，您应该在集群中安装 istio 和 kntaive。请遵循[此链接](https://knative.dev/docs/install/)获取安装说明。它需要 `knative 0.8.x 或更高版本`。


## Kubernetes-knative 部署

如果您选择使用 Kubernetes 生成器部署，请运行以下命令：

```shell
bash kubectl-knative-apply.sh (or) ./kubectl-knative-apply.sh
```

如果您选择使用 Helm 生成器部署，请运行以下命令：

```shell
bash helm-knative-apply.sh (or) ./helm-knative-apply.sh
```

`helm-knative-apply.sh` 将始终执行干净安装。任何具有相同标识的现有图表都会首先被删除，然后执行干净安装。

您可以通过运行以下 bash 命令来升级所有应用程序（如果您对生成的清单做了任何更改）：

```shell
bash helm-knative-upgrade.sh (or) ./helm-knative-upgrade.sh
```
